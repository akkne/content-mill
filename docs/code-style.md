# Стиль кода Content Mill

Правила применяются к приложениям в `backend/src/` и `frontend/`. Тесты бэкенда размещаются в `backend/tests/`. Отдельное [задание MVP](mvp.md) относится к прежнему однофайловому `frontend-mvp/legacy.html`.

## Общие правила

- Пиши короткий, понятный код без очевидных комментариев, заглушек и неиспользуемых файлов. Файлы адаптеров отключённых AI-моделей сохраняй по [правилу интеграций](architecture.md#интеграции-с-ai-моделями).
- Называй сущности по предметной области: ролик, сценарий, контент-план, бренд, публикация, метрика.
- На границах сценариев используй контракты, затем инфраструктурные реализации. Сценарии не зависят от FastAPI, ORM и SDK провайдеров.
- Держи секреты и локальные значения вне кода, в неотслеживаемом `.env`. После появления приложений перечисли нужные переменные в `.env.example`. Публичные переменные Next.js не должны содержать секреты.
- При изменении поведения обновляй документацию и проверяй затронутый сценарий.

## Python

- Следуй PEP 8, используй аннотации типов на публичных границах и форматтер/линтер, выбранный при создании приложения.
- Разделяй `domain/`, `application/`, `infrastructure/` и `presentation/` по чистой архитектуре. Внутри слоёв выделяй предметные папки по мере появления кода.
- Не смешивай обработку HTTP, правила предметной области и работу с внешними системами. HTTP-слой вызывает сценарий, сценарий использует контракт, инфраструктура реализует контракт.
- Используй SQLAlchemy ORM, модели как источник схемы и Alembic для версионирования. Новые миграции генерируй через `alembic revision --autogenerate`, просматривай и проверяй `alembic check`. Raw SQL в приложении и тестах не используй.
- Для каждой сторонней AI-модели делай отдельный файл адаптера существующего контракта операции. В сценариях вызывай контракт; провайдерские SDK, преобразование форматов и ограничения держи в адаптере и конфигурации выбора модели. При отключении модели убирай её из выбора для новых задач, сохраняя адаптер и [карточку модели](integrations/README.md).
- Обрабатывай ошибки явно; не скрывай исключения без контекста и понятного результата.

## Next.js и Tailwind CSS

- Для каждого пользовательского текста указывай обе версии через `t(ru, en)`. Получай переводчик через `useTranslator()` в клиентских компонентах и `await getTranslator()` в серверном коде. Проверяй также пустые состояния, загрузку, ошибки, подсказки и aria-подписи. Отделяй переводимые подписи от значений API и пользовательских данных. См. [решение о двух языках](decisions/0014-bilingual-interface.md).
- Используй TypeScript для нового интерфейса. Компоненты делай небольшими и называй по назначению.
- Все экраны и компоненты в `frontend/` оформляй утилитами Tailwind CSS 4 в `className`. Для адаптивной вёрстки, фокуса, выбора и отключённых элементов используй варианты Tailwind. В условиях указывай полные имена классов, чтобы сборщик мог их обнаружить.
- Цвета и тени обеих тем задавай в [globals.css](../frontend/src/app/globals.css) и подключай через `@theme inline`. Следуй [дизайн-токенам](DESIGN.md) и [дизайн-системе](design-system.md). Повторяющиеся наборы утилит для кнопок, полей и панелей бери из [ui-styles.ts](../frontend/src/app/ui-styles.ts).
- Для значения, которое становится известно только при рендеринге, передавай данные через CSS-переменную и применяй её в статической утилите Tailwind. Так устроен отступ папки по глубине дерева.
- Размещай секреты и серверные вызовы в серверном окружении Next.js. Клиентскому коду передавай только необходимые данные.
- Учитывай доступность: семантическая разметка, подписи полей, управление с клавиатуры, видимый фокус и состояния загрузки/ошибки.
