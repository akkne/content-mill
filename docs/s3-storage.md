# Структура S3 и доступ агентам Content Mill

В S3 лежат байты файлов. PostgreSQL связывает их с именами, папками, проектами и версиями. Поэтому запрос «возьми фото Анны в синей куртке» должен обрабатывать Content Mill: сервер находит версию по каталогу проекта, а затем читает нужный объект из S3.

## Физические ключи сегодня

В локальном Compose используется S3Mock. Имя бакета задаёт `S3_BUCKET`, по умолчанию это `content-mill`. Ниже показаны префиксы ключей объектов. [Конфигурация Compose](../compose.yaml) · [Адаптер S3](../backend/src/app/infrastructure/storage/s3_documents.py).

```text
s3://content-mill/
├── uploads/{project_id}/{upload_id}
└── projects/{project_id}/nodes/{node_id}/versions/{object_uuid}
```

| Ключ | Что содержит | Жизненный цикл |
| --- | --- | --- |
| `uploads/{project_id}/{upload_id}` | Байты загружаемого пользователем медиафайла или PDF. | Браузер получает подписанный PUT на 10 минут. При завершении сервер сверяет размер, SHA-256 и сигнатуру формата. Временные объекты очищаются по истечении срока загрузки. |
| `projects/{project_id}/nodes/{node_id}/versions/{object_uuid}` | Одну сохранённую версию документа, фото, аудио, видео или PDF, включая стартовые промпты проекта. | После проверки медиа сервер записывает постоянный объект и регистрирует версию. Редактор текста и создание стартовых документов записывают версии сразу в постоянный префикс. Новое содержимое получает новый ключ. |

Имя файла и расширение находятся в каталоге приложения. Например, в дереве «Аватары / Анна / Лицо крупным планом / Портрет.jpg» переименование папки меняет отображаемый путь. Байты обеих версий портрета остаются под прежними ключами. Пустая папка существует как запись дерева в PostgreSQL.

**Как разрешить ссылку.** `knowledge_nodes` хранит узел, проект, имя и родительскую папку. В `document_versions` у версии есть свой UUID, порядковый номер, формат, размер, SHA-256 и полный `storage_key`. Последний сегмент ключа генерируется отдельно. Для чтения нужно взять сохранённый `storage_key` из записи версии. Номер версии, UUID версии и UUID в ключе выполняют разные задачи. [Схема БД](database-schema.md) · [Запись и чтение версий](../backend/src/app/application/knowledge_service.py).

**Будущие результаты генерации.** По плану подготовленное фото персонажа, звуковой дубль и итоговый MP4 будут видны в папках соответствующего ролика. Для них подходит тот же механизм версий. Текущий серверный мок хранит данные демо-ролика в PostgreSQL и не создаёт в S3 финальное видео. [Формат передачи образа](video-agent-handoff.md) · [План производства](video-production-plan.md).

## Как подключать Claude Code и Codex CLI

Предлагаемая цепочка для обоих клиентов:

```text
Claude Code / Codex CLI → MCP в FastAPI → сценарий доступа к базе знаний
                                          ├─ PostgreSQL: права, поиск, версия, ключ
                                          └─ S3: содержимое выбранной версии
```

**Что нужно сделать на бэкенде.** Добавить в существующий монолит MCP по Streamable HTTP, например по пути `/mcp`. Реализовать проверку короткоживущего токена Content Mill, привязанного к пользователю и проекту, и инструменты `find_assets`, `read_document`, `preview_asset`. Каждое обращение должно проверять принадлежность узла и версии разрешённому проекту. Уже работают поиск, чтение версий и получение ссылки на скачивание. MCP-маршрут, выдача проектного токена для агента и генерация превью пока запланированы. [Решение о доступе агента](decisions/0009-agent-file-access.md).

**Как будет работать запрос.** Для «Возьми Портрет.jpg у Анны» агент вызывает поиск. Ответ содержит путь, тип и ID версии. При двух подходящих файлах из разных папок агент уточняет выбор. Для визуальной проверки запрашивает превью. Для генерации передаёт ID версии в задание. Бэкенд разрешает версию в оригинал и доставляет его провайдеру. В истории запуска сохраняется ID версии. Ключи S3 остаются в окружении бэкенда.

### Настройка клиентов после появления маршрута

Примеры рассчитаны на Claude Code и Codex CLI на том же компьютере, где запущен локальный Content Mill. Перед запуском клиента в его окружении должен быть `CONTENT_MILL_MCP_TOKEN`, выданный Content Mill для проекта. В примерах приведено только имя переменной. Для удалённого клиента потребуется доступный ему HTTPS-адрес MCP.

**Codex CLI.** Зарегистрировать HTTP-сервер и проверить конфигурацию. [Настройка MCP в Codex](https://developers.openai.com/codex/mcp).

```bash
codex mcp add content-mill --url http://localhost:8000/mcp --bearer-token-env-var CONTENT_MILL_MCP_TOKEN
codex mcp list
```

**Claude Code.** Добавить запись в проектный `.mcp.json`, объединяя её с существующими серверами. Claude Code подставляет значение из окружения при запуске. Затем проверить подключение через `claude mcp list` и открыть `/mcp` в сессии. [Настройка MCP в Claude Code](https://code.claude.com/docs/en/mcp).

```json
{
  "mcpServers": {
    "content-mill": {
      "type": "http",
      "url": "http://localhost:8000/mcp",
      "headers": {"Authorization": "Bearer ${CONTENT_MILL_MCP_TOKEN}"}
    }
  }
}
```

**Сеть и передача оригиналов.** В Compose бэкенд работает с `http://s3:9090`, а подписанная GET-ссылка по умолчанию использует `http://localhost:9090` и действует 15 минут. Для агента на ноутбуке и облачной модели это разные сети. Локальный MCP может сам прочитать файл и вернуть текст или превью. Для облачного видеогенератора бэкенд загружает выбранный файл через API провайдера либо выдаёт ссылку с доступным ему `S3_PUBLIC_ENDPOINT_URL`. Доступ извне к бакету целиком для этого не нужен.

**Проверка подключения.** В каждом клиенте открыть инструменты сервера, найти один известный файл по имени и прочитать конкретную версию. Повторить запрос с ID версии другого проекта и проверить отказ. После переименования исходника прежний ID должен открывать то же содержимое. До реализации адаптера команды выше показывают будущую конфигурацию, а доступность хранилища можно проверить существующим просмотром файлов в интерфейсе Content Mill.
