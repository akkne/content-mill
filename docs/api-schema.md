# Проект API: первый этап Content Mill

> Контракт первого этапа, 17 ноября 2026 года. Реализованы `GET /health`, сессии, пользователь, проекты и контекст клиента. Маршруты загрузки медиа и генерации контента ниже пока предлагаются. Типы генерации и модели будут уточнены позже. [План сервера](backend-foundation.md) и [роадмап фронтенда](frontend-roadmap.md) задают границы.

## Общие правила

- Базовый путь — `/api/v1`; таблицы ниже показывают его полностью. JSON в `snake_case`, ID — UUID, время — UTC ISO 8601.
- Все маршруты ресурсов требуют действующий access токен и серверную проверку доступа к проекту. Выход принимает refresh токен, чтобы работать и после истечения access. Роль из тела запроса не принимается. Пользователь видит только свои проекты и связанные с ними ресурсы.
- Для изменяемых ресурсов ответ содержит `revision`; изменение отправляет `If-Match`. Устаревшая ревизия даёт `409 conflict`, отсутствие заголовка — `428`.
- Списки возвращают `{items, next_cursor}`; запрос принимает `limit` и `cursor`. Ошибки: `{error: {code, message, request_id, fields?}}`; ожидаемые статусы — `400`, `401`, `403`, `404`, `409`, `422`, `429`, `503`.
- PostgreSQL хранит пользовательские записи и метаданные; все байты документов и медиа лежат в S3. API никогда не раскрывает постоянный объектный ключ. Временный URL выдаётся после проверки доступа.
- Для генерации `Idempotency-Key` обязателен. Повтор с тем же ключом и телом возвращает прежнюю задачу; другое тело с тем же ключом даёт `409`.

## Сессия и пользователь

| Метод и путь | Вход → результат |
| --- | --- |
| `POST /api/v1/auth/register` — работает | `{email, display_name, password}` → `201` и та же пара токенов, что при входе. Имя — 1–120 символов, пароль — 15–1024. Почта приводится к нижнему регистру. Занятая почта даёт `409`, неверные поля — `422`. |
| `POST /api/v1/auth/login` — работает | `{email, password}` → `{access_token, access_expires_at, refresh_token, refresh_expires_at}`. |
| `POST /api/v1/auth/refresh` — работает | `{refresh_token}` → новая пара токенов с ротацией. Повторное использование ротированного refresh отзывает семейство сессий. |
| `POST /api/v1/auth/logout` — работает | `{refresh_token}` → `204`, отзыв семейства сессий. |
| `GET /api/v1/me` — работает | Bearer access → `{id, display_name, projects: [{id, name, role: "owner"}]}`; до 100 последних проектов. Полный список с курсором доступен через `/projects`. |

Регистрация допускает 30 попыток за 15 минут с адреса клиента API, после чего возвращает `429`. Для запросов через Next.js это общий адрес сервера интерфейса. Проверяется формат почты. Подтверждение владения ящиком по письму не предусмотрено.

Access действует 15 минут, refresh — 14 дней. Оба значения случайные; сервер хранит только их хеши. Next.js сохраняет токены в HttpOnly cookie, обновляет пару при истечении access и не отдаёт их клиентскому JavaScript.

## Проекты и контекст клиента

| Метод и путь | Вход → результат |
| --- | --- |
| `GET /api/v1/projects` / `POST /api/v1/projects` — работают | Список `{items, next_cursor}` с `limit` 1–100 и курсором; создание `{name}` → `201 Project`. Дерево базы знаний будет добавлено отдельно. |
| `GET /api/v1/projects/{project_id}` / `PATCH /api/v1/projects/{project_id}` — работают | Сведения и переименование `{name}` по `If-Match` ревизии проекта. |
| `GET /api/v1/projects/{project_id}/context` / `PUT /api/v1/projects/{project_id}/context` — работают | Структурированный контекст: `{description, audiences: string[], products: [{name, description}], facts: [{text, source_url?}], tone_of_voice, forbidden_terms: string[], source_version_ids: UUID[]}`. Поле `tone_of_voice` сохранено в контракте для совместимости с существующими данными, но убрано из редактора; имя и язык каждого голоса задаются у аудиофайла. `PUT` с `If-Match` создаёт новую ревизию. `PATCH` по тому же адресу с `If-Match` заменяет только переданные поля. Список передаётся целиком, пустой список очищает поле. `source_version_ids` принимает версии текстовых документов этого проекта. |

`Project` содержит `id`, `name`, `owner_id`, `revision`, `created_at`. Контекст и принадлежность к проекту находятся в PostgreSQL. Сейчас доступ есть только у владельца; чужой проект возвращает `404`. Роли редактора и наблюдателя, состав команды и приглашения будут определены отдельно. Контекст может ссылаться на готовые версии текстовых документов.

## База знаний и файлы

Все пути в таблице начинаются с `/api/v1/projects/{project_id}`.

| Метод и суффикс | Вход → результат |
| --- | --- |
| `GET /nodes?parent_id={id}` / `POST /nodes` — работают | Содержимое папки; создание `{parent_id?, name, kind: folder/document}` → `201 Node`. |
| `GET /nodes/tree` — работает | Все активные узлы проекта для отображения дерева. |
| `GET /nodes/{node_id}` / `PATCH /nodes/{node_id}` — работают | Метаданные; `{name}` с `If-Match` для переименования. |
| `POST /nodes/{node_id}/move` / `DELETE /nodes/{node_id}` — работают | `{new_parent_id}` с `If-Match`; архивирование узла вместе с потомками. Перенос в собственного потомка отклоняется. |
| `GET /nodes/{node_id}/versions` — работает для документов и медиа | Версии с форматом, размером, контрольной суммой и датой. |
| `GET /nodes/{node_id}/content` / `PUT /nodes/{node_id}/content` — работают | Текстовый документ; `PUT {content, format}` с `If-Match` создаёт неизменяемую версию в S3. |
| `POST /files/uploads` | `{parent_id?, node_id?, name, mime_type, size_bytes, sha256}` → `{upload_id, upload_url, expires_at}`. Для нового файла указан `parent_id`, для новой версии — `node_id` и заголовок `If-Match`. Браузер выполняет PUT по ссылке с указанным Content-Type. |
| `POST /files/uploads/{upload_id}/complete` | Проверяет загруженный объект → готовые `Node` и `FileVersion`. |
| `GET /nodes/{node_id}/download?version={n}` | Короткоживущий URL для просмотра или скачивания после проверки доступа. |
| `POST /files/examples` | Импорт папки «Пример проекта» с документами и медиа из демо. |
| `PATCH /nodes/{node_id}/voice` | Аудиофайл, `If-Match`, `{name, language, model?}` → обновлённый узел. |
| `GET /search?q=...` — работает | Поиск по названиям и тексту текущих версий документов проекта → узлы; путь вычисляется из дерева на клиенте. Не более 100 результатов. |

`Node` содержит `id`, `project_id`, `parent_id`, `kind`, `name`, `revision`, `archived_at`. `DocumentVersion` содержит `id`, `node_id`, `version`, `format`, `size_bytes`, `sha256`, `created_at`; ключ S3 остаётся серверным. Для медиа поле `format` содержит MIME-тип. Незавершённая загрузка хранится отдельно от узлов. Документ в S3 остаётся источником содержимого; текст текущей версии дополнительно хранится в PostgreSQL для поиска. Версии, созданные до появления индекса, читаются из S3 при поиске.

Реализованы дерево, текстовые документы Markdown/plain text до 1 МБ, история неизменяемых версий, ссылки контекста на версии документов и поиск по названиям и тексту. Содержимое хранится в S3, метаданные и поисковый текст — в PostgreSQL. Подписанная ссылка на загрузку действует 10 минут, на просмотр — 15 минут. Подтверждение сверяет размер, SHA-256 и сигнатуру, сохраняет неизменяемую копию и допускает повтор запроса. Просроченные загрузки очищаются автоматически.

## Создание контента

| Метод и путь | Вход → результат |
| --- | --- |
| `GET /api/v1/projects/{project_id}/contents` / `POST /api/v1/projects/{project_id}/contents` | Список; `{goal, content_type, brief, context_revision, source_version_ids[], options}` → `201 ContentDraft`. Допустимые `content_type` и `options` утверждаются после выбора первого сценария и моделей. |
| `GET /api/v1/projects/{project_id}/contents/{content_id}` / `PATCH /api/v1/projects/{project_id}/contents/{content_id}` | Черновик, использованные источники и результат; изменение задания по `If-Match` до запуска. |
| `POST /api/v1/projects/{project_id}/contents/{content_id}/generations` | `Idempotency-Key` и `{instructions?}` → `202 GenerationRun`. Запись сохраняет снимок версий контекста и источников. |
| `GET /api/v1/projects/{project_id}/contents/{content_id}/generations` / `GET /api/v1/projects/{project_id}/contents/{content_id}/generations/{run_id}` | История и состояние попытки: `queued/running/succeeded/failed`, этап, ошибки, ID документов и медиа результата. |

`ContentDraft` и `GenerationRun` хранятся в PostgreSQL. Полученные документы, исходники и медиа — в S3 с версиями; сервер записывает фактическую модель и её выходы. Конкретные шаги генерации, структура результата, длительность ролика и формат кадра будут закреплены после описания моделей. План прежнего полного видеоконвейера остаётся в [общем роадмапе](implementation-roadmap.md), но не задаёт эндпоинты первого этапа.

## Проверки контракта при реализации

Права на чужой проект и файл, отзыв и повтор refresh токена, конфликт ревизий, повтор `Idempotency-Key`, незавершённая загрузка, подмена S3-объекта, сохранение версий источников при повторной генерации.
