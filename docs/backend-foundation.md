# Основа бэкенда для первого этапа

> План, не описание работающего API. Сейчас `backend/src/app/main.py` содержит только `/health`. Сервер остаётся одним FastAPI-приложением. Контракт первого этапа предложен в [схеме API](api-schema.md), последовательность интерфейса — в [роадмапе фронтенда](frontend-roadmap.md).

## Границы данных

- PostgreSQL хранит **все данные пользователей**: учётные записи, проекты и доступ, структурированный контекст клиента, дерево базы знаний, метаданные и версии файлов, сессии refresh токенов, задания и результаты генерации, статусы, связи и журнал попыток.
- S3-совместимое хранилище содержит **все документы и файлы**: текстовые документы, исходники, изображения, аудио, видео и результаты генерации. PostgreSQL хранит только метаданные, идентификатор объекта, версии и при необходимости извлечённый текст для поиска; этот текст не заменяет документ в S3.
- Объектные ключи основаны на стабильных ID и версиях. Дерево папок — представление записей PostgreSQL. Доступ к файлу и временной ссылке выдаётся только после проверки проекта и роли.
- Запись новой версии документа и завершение загрузки сначала проверяют наличие объекта, затем публикуют метаданные готовой версии. Незавершённые загрузки не видны в дереве. Содержимое готовых версий не перезаписывается.

## Вход и сессии

- С первого релиза нужны короткоживущий access токен и обновляемый refresh токен. Refresh сессия хранится в PostgreSQL в виде проверяемого хеша с пользователем, сроком действия, временем отзыва и семейством ротации. При обновлении прежний refresh становится недействительным; повторное использование отозванного токена отзывает семейство.
- Выход отзывает текущую refresh сессию. Access проверяется на каждом защищённом запросе; полномочия проекта сверяются с PostgreSQL, а не доверяются роли из интерфейса.
- Механизм первичной проверки личности, формат access, срок жизни, способ доставки и защита браузерной сессии выбираются перед кодом авторизации. Демо Google/Microsoft — только макет и не задаёт провайдера. В API нельзя возвращать хеши, секреты и объектные ключи.

## Сценарии сервера

1. Учётная запись и проект: определить личность, создать/прочитать проект, проверить доступ к каждому ресурсу.
2. Контекст клиента: сохранять структурированные факты и ссылки на версии документов; конфликт изменения возвращать явно.
3. База знаний: управлять деревом, версиями и S3-загрузкой/скачиванием; поддержать поиск по метаданным и извлечённому тексту.
4. Контент: сохранять задание и снимок использованных версий контекста, запускать операцию создания, вести статус и результат, не терять историю повторных попыток. После выбора моделей добавить адаптер каждой модели отдельным файлом и [карточку интеграции](integrations/README.md).
